# Threat model

Scope: the ingestion API, stores, detection/investigation services, portal, LLM and GitHub integrations. Method: STRIDE-style walk through each trust boundary.

## Assets
1. Telemetry (pseudonymous, but still sensitive in aggregate).
2. Source code and commit metadata fetched from GitHub.
3. Credentials: API token, GitHub token, LLM API key.
4. Integrity of incident reports (people act on them).

## Trust boundaries and threats

| Boundary | Threat | Mitigation | Residual |
|---|---|---|---|
| Client to ingestion API | Spoofed or flooding writers | Optional bearer token (`AIL_API_TOKEN`, constant-time compare), 10 MB body cap, bounded queue with `503`/`Retry-After`, optional per-client token bucket (`AIL_RATE_LIMIT`) returning `429`/`Retry-After`; the SDK honours both | The limiter keys on the connecting address, so behind a reverse proxy all clients look alike unless the proxy limits them. |
| Client to ingestion API | Personal data sent in events | Strict schema (`extra="forbid"`), PII-looking dimension keys rejected, docs tell senders what not to send | Free-text *values* in allowed fields are not inspected. |
| Client to ingestion API | Malformed or hostile payloads | Per-item validation, length limits, finite-number checks, parameterised SQL only | |
| Client to ingestion API | Replay / duplicate delivery corrupting counts | Event-id de-duplication; aggregates only updated for new events | Events without ids are de-duplicated by content hash only. |
| Portal | XSS from telemetry-derived strings | All dynamic text inserted via `textContent`/text nodes; no `innerHTML` with data | |
| Portal / read API | Unauthenticated reads | Read endpoints are open by default for local use; `AIL_READ_TOKEN` requires a bearer token on every `GET /api/v1/*` and `/metrics` (constant-time compare); the portal asks for the token and keeps it in `sessionStorage` for the tab | A single shared token, no per-user identity or scopes. The portal shell itself is public (it contains no data). |
| Investigation to LLM | Prompt injection via commit messages, diffs or telemetry strings | Commit messages are never sent; model sees numbered evidence generated by code; system prompt says evidence is data; output validated (schema, citations, numbers, hashes); no tools or actions are available to the model | A model could still produce a misleading *interpretation* using valid numbers; hypotheses are labelled unverified. |
| Investigation to LLM | Data exfiltration to a third party | Default provider is offline; external providers are opt-in via env; https enforced except localhost; only evidence statements are sent | Statements include cohort names and versions. Use a local model for sensitive fleets. |
| Investigation to GitHub | Over-privileged token | Read-only endpoints; token scope guidance: `contents:read`, `metadata:read`; issue creation needs `issues:write` and an explicit `--create` flag | OAuth app flow not implemented; a personal token is used. |
| Investigation to GitHub | SSRF / path injection through repository names | Repository must match `owner/name`; base URL is fixed to `api.github.com` | |
| Config and secrets | Secrets committed | Secrets only via environment; `.gitignore` excludes `.env*` and databases; `.env.example` has no values; gitleaks runs in CI | Scans run in CI after a push; a leaked secret in history must be rotated. |
| Storage | Tampering with the database file | File permissions only | No encryption at rest or signing. |
| Supply chain | Malicious dependency | Small dependency set (numpy, pydantic, fastapi, uvicorn, httpx, pyyaml); no front-end build chain; `pip-audit` in CI and Dependabot for pip, Actions and Docker | Dependencies are not hash-pinned. |
| Real-device collection | Covert or excessive collection | The agent refuses to run without a consent file; `enroll` lists every signal and prompts; `preview` prints the exact payload; `revoke` deletes consent and the device id; signals are a fixed allowlist; the device id is random and local; no hostname, user, process, file, network or location data is read | The consent file is user-writable, so a local attacker could change it; the agent trusts the local user. Agent code has not had an external review. |

## Privacy design rules
- Schema contains no direct identifiers; `device_id` must be a random or salted identifier chosen by the sender.
- Demos run on synthetic data.
- Any real-device collector must be opt-in, show exactly what it sends, and send only the documented signals.
